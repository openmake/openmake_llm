01 · 개요

고친 코드가 실사용 환경에 닿기까지

로컬 장비에서 고치고(로컬 개발), 세 환경 — dev · staging · online — 을 차례로 거쳐 올린다. 환경은 서로 .env·docker·PM2 가 분리되어 있어, 하나가 꼬이면 그것만 지우고 다시 설치할 수 있다. 진입점은 scripts/env/omk.sh 하나다.

용어

이름장소 · 경로무엇무엇을 담나
로컬 개발로컬 장비
작업 클론 (예: ~/openmake/openmake_llm)		omk dev up — 고치면서 바로 보는 핫 리로드. 환경이 아니다지금 고치고 있는 소스 (커밋 전 포함)
환경 dev개발 서버
~/.openmake/dev		omk env install dev 로 설치한 배포본브랜치 dev
환경 staging스테이징 서버
~/.openmake/staging		설치한 배포본. 데이터를 유지한다브랜치 main
환경 online온라인 서버
~/.openmake/online		실사용최신 릴리스 태그
dev 는 브랜치 이름이기도 하고 환경 이름이기도 하다

브랜치 dev 는 feature/* 가 모이는 git 브랜치이고, 환경 dev 는 그 브랜치를 설치해 돌리는 곳이다. staging 이 main 을 따르는 것과 같은 관계다.

전체 흐름

위 줄은 git(코드가 어디에 있는가), 아래 줄은 도는 곳(이름 · 장소 · 경로)이다. 번호는 단계별 작업 순서의 번호와 같다.

로컬 개발 — 고치면서 바로 본다 dev — 합쳐진 dev 가 설치되고 도는가 staging — 합쳐진 main 이 올라가도 되는가 online — 실사용

세 가지 원칙

원칙 1
배포는 전부 수동이다

머지·릴리스만으로는 어떤 환경도 바뀌지 않는다. 사람이 omk env update <env> 를 실행해야 올라간다.

원칙 2
앞 단계를 통과해야 다음으로 간다

환경 dev 통과 전에는 main 으로 올리지 않는다. staging 통과 전에는 릴리스하지 않는다.

원칙 3
online 은 릴리스 태그만 따른다

main 은 개발이 모이는 곳이다. staging 에서 확인하기 전의 main 을 운영이 받지 않는다.

한눈에 보는 단계

#어디서무엇을명령
①로컬 개발브랜치 dev 에서 브랜치를 따 핫 리로드로 수정 → 로컬 테스트 → pushomk dev up
②GitHubfeature/* → dev PR → CI → 일반 머지gh pr create --base dev
③환경 dev합쳐진 dev 가 실제로 설치되고 도는지 확인omk env update dev

⑤환경 staging머지된 main 을 기존 데이터 위에서 update 로 확인omk env update staging
⑥환경 staging확인을 마친 커밋을 기록omk env verify staging
⑦GitHub릴리스 PR 머지 → vX.Y.Z 태그릴리스 PR 머지
⑧환경 online새 릴리스 태그로 올리고 스모크 확인omk env update online

  • 이름 있는 인스턴스의 포트는 한 칸 옆(52417 / 3010 / 5433 / 6380)부터 잡고, 쓰이고 있으면 옮긴다. omk 는 포트를 기억하지 않는다 — 실제 값은 omk env status <env> 로 본다.
  • 충돌 판정은 설치하는 순간 열려 있는 포트만 본다. 같은 장비에서 나란히 쓸 환경·로컬 개발은 띄워 둔 채 설치한다.

02 · 작업 순서

단계별 작업 순서

브랜치를 따는 것부터 online 에 올리는 것까지. 각 단계 끝의 통과 조건을 채운 뒤 다음으로 간다.

omk 명령을 어떻게 부르나

환경이 설치된 호스트에서는 omk … 로 부른다(래퍼 ~/.openmake/bin/omk). 래퍼는 online → staging → 그 밖의 환경 순으로 처음 찾은 환경의 스크립트를 실행한다. 환경이 하나도 없는 장비(로컬 개발만 하는 로컬 장비)에서는 작업 클론의 스크립트를 직접 부른다: scripts/env/omk.sh …

1
로컬 개발 · 로컬 장비

브랜치를 따서 고치고, 로컬에서 확인하고, push

브랜치는 origin/dev 에서 딴다. 핫 리로드로 고치면서 확인한다.

# 브랜치
git fetch origin
git switch -c feature/<주제> origin/dev

# 로컬 개발 — 최초 1회 준비, 그 뒤로는 up 만
scripts/env/omk.sh dev setup
scripts/env/omk.sh dev up

# 고친 뒤 — CI 는 40분쯤 걸린다. 올리기 전에 여기서 먼저 돌린다
npm test
npm run lint
bash scripts/env/omk.test.sh        # omk.sh 를 고쳤을 때

git push -u origin feature/<주제>

통과 조건로컬 테스트·lint 통과, 로컬 개발에서 바꾼 기능이 동작, 원격에 push 됨

고친 것에 따라 무엇을 다시 해야 하는지는 로컬 개발 — 고친 뒤 할 일.

2
GitHub

PR 로 브랜치 dev 에 합친다

dev 에는 직접 push 하지 않는다. PR 을 열면 CI 가 돌고, 통과해야 머지할 수 있다. 일반 머지로 합친다.

gh pr create --base dev
gh pr checks --watch               # CI 진행 보기
gh pr merge --merge                # 일반 머지 (squash 아님)

CI 는 테스트·빌드·lint 를 본다. "설치해서 도는지"는 보지 않는다 — 그것은 다음 단계다.

통과 조건CI Gate 통과, origin/dev 에 합쳐짐

3
환경 dev · 개발 서버

합쳐진 dev 가 실제로 설치되고 도는지 확인

브랜치 dev 를 받아 빌드하고 PM2 로 띄운다. 로컬 개발에서 되던 것이 여기서 안 될 수 있다 — 빌드 실패, push 에서 빠진 파일, PM2 기동 문제는 여기서만 드러난다.

# 처음 한 번 — 기본으로 브랜치 dev 를 설치한다
omk env install dev --tailscale

# 그 뒤로는 dev 에 머지될 때마다
omk env update dev
omk env status dev

확인할 것: 설치가 끝까지 되는가 → 바꾼 기능 → 기본 동작(채팅 · 웹 검색 · 에이전트 작업 · 아티팩트 내보내기).

통과 조건요약에 [ERR] 없음, omk env status dev 의 health 가 OK, 위 기능 확인

문제가 나오면 ① 로 돌아가 고친다. 자세한 것은 환경 dev.

4
GitHub

dev 를 main 으로 올린다

dev 에 쌓인 것을 한꺼번에 올린다. CI 를 다시 지나고 일반 머지한다.

gh pr create --base main --head dev
squash 하지 않는다

squash 는 dev 와 main 의 연결을 끊어, 다음에 올릴 때마다 이미 올린 변경이 충돌한다. 일반 머지라 dev 의 커밋 제목이 그대로 main 에 들어가고 release-please 가 그것을 CHANGELOG 에 쓴다 — 커밋 제목은 feat(…): · fix(…): 형식을 지킨다.

통과 조건③ 환경 dev 통과, CI Gate 통과, main 에 머지됨

5
환경 staging · 스테이징 서버

머지된 main 을 기존 데이터 위에서 update 로 확인

staging 은 머지된 main 을 본다 — 합쳐진 결과와, update·마이그레이션 경로. online 도 update 로 올라가므로 같은 길을 먼저 밟는다.

omk env update staging
omk env status staging

통과 조건update 가 끝까지 됨, 마이그레이션이 기존 데이터에서 통과, 합쳐진 기능 확인

자세한 것은 환경 staging.

6
환경 staging · 스테이징 서버

확인을 마친 커밋을 기록

이 기록이 있는 커밋에서 나온 릴리스만 online 에 올라간다.

omk env verify staging
omk env verify staging --list      # 기록 보기

# 설치된 클론의 origin 은 https(읽기 전용)다 — push 할 주소를 준다
OMK_VERIFY_PUSH_URL=git@github.com:openmake/openmake_llm.git omk env verify staging

통과 조건기록이 origin 에 남음. verify 뒤에 main 에 머지가 더 들어왔으면 ⑤ 부터 다시

자세한 것은 릴리스 게이트.

7
GitHub

릴리스 PR 을 머지해 태그를 만든다

release-please 가 만든 릴리스 PR 을 머지하면 vX.Y.Z 태그가 찍힌다. 태그는 머지한 순간의 main 에 찍히므로, ⑥ 뒤에 main 에 들어온 것이 없을 때 머지한다.

통과 조건새 vX.Y.Z 태그

8
환경 online · 온라인 서버

새 릴리스 태그로 올리고 스모크 확인

올리기 직전에 DB 백업을 한 번 뜬다(실패하면 올리지 않는다). 게이트가 켜져 있으면 ⑥ 의 기록을 본다.

omk env update online
omk env status online

스모크: 접속 200 · 로그인 · 채팅 1회 · omk env status online. 무거운 검증은 하지 않는다.

통과 조건스모크 통과

자세한 것은 환경 online.

03 · 로컬 개발

로컬 개발 — 고치면서 바로 본다

로컬 장비의 작업 클론 안에서 쓴다. 환경이 아니다 — ~/.openmake 아래에 두지 않고, 인스턴스 이름 local 로 앱이 PM2 없이 포그라운드에서 돈다.

명령

scripts/env/omk.sh dev setup          # 최초 1회 — 툴체인·.env·의존성·DB·마이그레이션·검색·런타임 이미지·게이트웨이·기본 모델
scripts/env/omk.sh dev up             # DB/Redis/SearXNG/게이트웨이 + api + web (+ bench) — Ctrl+C 로 종료
scripts/env/omk.sh dev up api         # 개별: deps | api | web | bench
scripts/env/omk.sh dev up --tailscale # 다른 기기에서 보기 (또는 --host <이름|IP>)
scripts/env/omk.sh dev status
scripts/env/omk.sh dev down           # DB/Redis/SearXNG/게이트웨이 정지 (데이터 유지)
scripts/env/omk.sh dev reset          # 컨테이너·볼륨 삭제 (소스·.env 유지). --keep-data 면 볼륨은 남긴다

openmake_bench 가 옆 디렉터리(../openmake_bench)에 있으면 같이 띄운다.

setup 옵션

환경 설치(omk env install)와 이름도 뜻도 같다.

옵션하는 일
--no-runtime-images런타임 이미지(약 7GB) 빌드를 뺀다. 에이전트 작업·아티팩트 내보내기는 동작하지 않는다
--no-searxng웹 검색 컨테이너를 뺀다
--no-litellm게이트웨이를 뺀다 — .env 의 LLM 주소를 직접 채워야 한다
--no-default-model기본 모델(1.7B)을 띄우지 않는다
--llm-base-url U --llm-model M게이트웨이 뒤에 둘 업스트림. 이미 있는 Ollama 등 (--llm-api-key K 는 선택)
 
# 예 — 이미 있는 Ollama 를 쓰고, 이미지 빌드는 뺀다
scripts/env/omk.sh dev setup --no-runtime-images \
  --llm-base-url http://localhost:11434/v1 --llm-model <모델 이름>

고친 뒤 할 일

코드만 고쳤으면 dev up 재시작, 설치되는 것이 바뀌었으면 dev setup.

고친 것할 일
웹 화면 apps/web없음 — 저장하면 바로 반영
API apps/apidev up 을 끄고 다시 띄운다 — API 는 감시 재시작이 없다
공용 패키지 packages/*npm run build:packages → dev up 재시작
의존성 package.jsondev setup
DB 마이그레이션dev setup
런타임 이미지 Dockerfiledev setup
omk.sh · 설치 스크립트dev setup
setup 을 다시 돌릴 때

dev up 을 먼저 끈다 — .env 가 바뀌면 API 를 어차피 다시 띄워야 한다. dev setup 은 지우지 않는다: DB 볼륨과 .env 의 기존 값(비밀번호·암호화 키)은 그대로 두고 없는 것만 채운다. 지우는 것은 dev reset 이다.

환경과 같은 것, 다른 것

검색·런타임 이미지·게이트웨이·기본 모델은 환경 설치와 같은 함수(stack_ensure)로 준비한다. 그래서 설치 직후 바로 채팅이 된다. 다른 것은 셋뿐이다.

  • 앱을 빌드하지 않는다 — ts-node · next dev 로 돈다
  • 앱을 PM2 에 올리지 않는다 — concurrently 아래 포그라운드
  • .env 의 NODE_ENV 가 development 다

호스트의 환경들과 같이 쓰는 것, 따로 두는 것

같이 쓰는 것 (호스트에 하나)따로 두는 것 (local)
Docker 엔진 — macOS 는 Colima VM openmakePostgreSQL · Redis (openmake-local-*) — 브랜치의 마이그레이션이 환경의 DB 를 바꾸지 않게
기본 모델 서버 — PM2 omk-llamacpp. 모델 1.8GB 는 한 번만 받는다게이트웨이 — PM2 openmake-litellm-local. 환경이 없어도 채팅이 된다
런타임 이미지의 레이어 (캐시 재사용)런타임 이미지의 태그 :local · SearXNG · 작업 공간
  • .env 의 LLM_BASE_URL 을 직접 넣어 둔 작업 클론은 건드리지 않는다. omk 가 바꾸는 것은 비어 있거나, 자리표시자(http://localhost:4000 인데 그 포트에 아무것도 없음)이거나, omk 가 넣은 게이트웨이 주소일 때뿐이다.
  • 게이트웨이와 기본 모델 서버는 dev up 의 Ctrl+C 뒤에도 남는다. 재부팅 등으로 내려가 있으면 dev up 이 다시 띄운다.
  • 작업 클론이 여럿이면 게이트웨이 하나(local)를 같이 쓴다.
04 · 환경 dev

"합쳐진 dev 가 실제 환경에서 도는가"

개발 서버에 설치한 배포본이다. 브랜치 dev 를 따르고, main 으로 올리기 전에 거친다. 데이터는 버리는 것이다 — 꼬이면 망설이지 말고 reset.

명령

omk env install dev --tailscale      # 처음 한 번 — 기본으로 브랜치 dev 를 설치한다
omk env update dev                   # dev 에 머지될 때마다
omk env status dev
omk env logs dev
omk env reset dev --reinstall        # 꼬였을 때

머지 전에 따로 보고 싶은 브랜치 — 임시 환경

위험한 변경이나 남의 PR 은 환경 dev 를 건드리지 않고 임시 환경에 올린다. 끝나면 지운다.

omk env install pr-123 --ref feature/<주제>
omk env reset pr-123

omk.sh 자체를 고친 브랜치는 래퍼 대신 그 소스의 스크립트를 직접 부른다: <작업 클론>/scripts/env/omk.sh env install pr-123 --ref feature/<주제>

브랜치 dev 가 없는 저장소

포크처럼 브랜치 dev 가 없는 저장소에서는 --ref main 을 준다. openmake_bench 도 브랜치 dev 가 없다 — 환경 dev 에 --bench 로 붙이면 bench 는 main 을 쓴다.

확인할 것

  1. 설치·update 가 끝까지 되는가
  2. 바꾼 기능
  3. 기본 동작 — 채팅 · 웹 검색 · 에이전트 작업 · 아티팩트 내보내기

dev 가 증명하는 것은 배선과 구조다. 기본 모델(1.7B)은 작다 — 답변 품질과 에이전트 성공률은 판단하지 않는다.

할 것 / 하지 말 것

할 것하지 말 것
브랜치 dev 에 머지될 때마다 omk env update dev — 설치가 끝까지 되는지부터 본다환경 dev 를 건너뛰고 dev 를 main 으로 올리지 않는다 — CI 는 "설치해서 도는지"를 보지 않는다
바꾼 기능 + 기본 동작을 확인한다dev 의 결과로 답변 품질·에이전트 성공률을 판단하지 않는다
꼬이면 omk env reset dev --reinstall남기고 싶은 데이터를 dev 에 두지 않는다
문제가 나오면 로컬 개발에서 고쳐 → push → 브랜치 dev 에 머지 → omk env update dev환경 디렉터리(~/.openmake/dev/llm)의 소스를 직접 고치지 않는다
머지 전에 따로 볼 브랜치는 임시 환경에 올린다환경 dev 에 --ref 만 바꿔 다시 install 하지 않는다 — 이미 있는 클론이 재사용되어 이전 브랜치가 설치된다
무거운 실험(새 모델, 설정 변경, 일부러 깨뜨리기)은 여기서 한다임시 환경을 방치하지 않는다 — 환경마다 DB·게이트웨이·이미지가 따로 생긴다
05 · 환경 staging

"합쳐진 main 이 online 에 올라가도 되는가"

항상 main 을 따른다. 데이터를 유지한 채 update 경로로 올려, online 이 밟을 길을 먼저 밟는다.

명령

omk env update staging            # main 에 머지될 때마다
omk env status staging
omk env verify staging            # 확인을 마친 뒤

확인할 것

  1. update 가 끝까지 되는가 (ff-only → build → migrate → restart)
  2. 마이그레이션이 기존 데이터에서 도는가
  3. 여러 PR 이 합쳐진 결과의 기능 — 기능 확인은 여기까지 끝낸다

할 것 / 하지 말 것

할 것하지 말 것
항상 main (--ref 없이 설치). 머지될 때마다 omk env update staging--ref feature/* 로 PR 을 시험하지 않는다 — 그것은 임시 환경의 일이다
update 경로로 올린다습관적으로 reset → 재설치하지 않는다 — 마이그레이션이 기존 데이터에서 도는지 볼 수 없게 된다
데이터를 유지한다. reset 은 정말 꼬였을 때만실사용 데이터·비밀값을 가져다 넣지 않는다
여러 PR 이 합쳐진 결과의 기능 확인은 여기까지 끝낸다통과하기 전에 릴리스 PR 을 머지하지 않는다
확인이 끝나면 omk env verify staging확인하지 않고 verify 하지 않는다. verify 뒤에 머지가 더 들어왔으면 update → 확인 → verify 를 다시 한다
문제가 나오면 수정(① 부터) 또는 revertstaging 에서 직접 핫픽스하지 않는다
06 · 환경 online

"실사용"

최신 릴리스 태그로만 올라간다. 확인은 스모크만 한다 — 무거운 검증은 CI 와 staging 에서 끝났어야 한다.

명령

omk env update online             # 새 릴리스 태그가 있을 때만 올라간다. 직전에 DB 백업
omk env status online
omk env backup online --schedule  # 매일 03:30 백업 — 한 번 걸어 둔다

스모크

  1. 접속 200
  2. 로그인
  3. 채팅 1회
  4. omk env status online

문제가 났을 때

수정 → 새 릴리스 → update 가 기본이다. 급하면 이전 태그로 되돌리고 그 환경 디렉터리에서 ./openmake_llm.sh deploy.

할 것 / 하지 말 것

할 것하지 말 것
릴리스 직후 omk env update onlinemain HEAD · feature/* 를 올리지 않는다 (--ref 로 브랜치를 주지 않는다)
스모크만 한다부하 시험·대량 평가·동시 다발 요청을 하지 않는다 — 운영 모델 서버를 공유한다
매일 백업을 걸어 둔다omk env reset online 을 하지 않는다 — 볼륨(DB)까지 지운다
게이트를 켜 둔다 (.env 의 OMK_RELEASE_GATE=1)--force-unverified 를 습관적으로 쓰지 않는다
호스트별 값(도메인·모델 서버 주소·키)은 그 환경의 .env · litellm.env 에만 둔다저장소에 호스트 경로·주소·키를 적지 않는다
문제가 나면 수정 → 새 릴리스 → updateonline 에서 실험·설정 시험·모델 교체 시험을 하지 않는다
07 · 릴리스 게이트

staging 에서 확인한 커밋만 online 에

릴리스 태그는 릴리스 PR 을 머지한 순간의 main 에 찍힌다. staging 을 마지막으로 올린 뒤에 머지된 PR 은 확인 없이 릴리스에 들어간다 — 게이트는 그 경우를 막는다.

# 스테이징 서버 — 기능·마이그레이션 확인을 마친 뒤
omk env verify staging            # 검사(깨끗한 작업 트리 · origin/main 에 있는 커밋 · health) → origin 에 기록
omk env verify staging --list

# 온라인 서버 — 한 번 켠다 (.env 에 OMK_RELEASE_GATE=1, 또는 설치할 때 --release-gate)
omk env update online             # 확인된 릴리스만 올라간다
기록origin 의 refs/omk/verified/<커밋>. 브랜치·태그가 아니라 GitHub 화면에는 보이지 않는다. 환경들이 다른 호스트에 있어도 읽힌다
통과 조건기록된 커밋이 릴리스 태그의 조상이고, 그 사이에 바뀐 것이 릴리스 메타데이터뿐이다 (버전·CHANGELOG). 릴리스 커밋에 섞인 의존성 변경은 거부한다
거부되면아무것도 바꾸지 않고 종료 코드 2. 환경은 지금 버전 그대로 돈다
급한 수정omk env update online --force-unverified — 물어본 뒤 진행하고 ~/.openmake/online/logs/release-gate.log 에 남긴다
범위게이트는 켠 환경에서만 동작한다. 외부 설치본은 기본으로 꺼져 있다

스테이징 서버의 쓰기 권한

verify 는 origin 에 push 한다. 설치된 클론의 origin 은 https(읽기 전용)이므로 push 할 주소를 따로 준다.

OMK_VERIFY_PUSH_URL=git@github.com:openmake/openmake_llm.git omk env verify staging
방법설명
SSH agent forwarding (권장)ssh -A staging-host 로 들어가 실행한다 — 호스트에 자격 증명이 남지 않는다
쓰기 권한 deploy key호스트에 저장해야 할 때. 그 키로 main · v* 태그를 고칠 수 없게 브랜치 보호를 먼저 확인한다
08 · 설치

아무것도 없는 호스트에서 한 줄

옵션 없이 설치하면 게이트웨이와 기본 모델까지 채워져, 채울 것 없이 채팅이 된다.

Windows 네이티브는 지원하지 않는다 — WSL2(Ubuntu) 안에서 같은 스크립트를 쓴다(omk.ps1).

한 번에 되는 일

  1. git 확인 → openmake_llm 클론
  2. install.sh --minimal — Node 24 · Docker · PM2, .env 시크릿, PostgreSQL · Redis, 마이그레이션, 빌드, PM2 기동, health

  5. Caddy 프록시 → --tailscale / --host 를 줬으면 그 주소 허용

09 · 복구

꼬였을 때 — 지우고 다시

reset 은 환경 이름만으로 지울 대상을 계산한다. .env 가 깨졌어도 동작한다.

online 에는 쓰지 않는다

omk env reset online 은 DB 볼륨까지 지운다. 옮길 때는 db-dump → db-restore.

omk env reset staging --reinstall            # 전부 지우고 같은 브랜치로 재설치
omk env reset staging --keep-env --reinstall # .env(LLM 키·API 키)는 백업했다가 복원
omk env reset staging --keep-data            # DB 볼륨은 남김 (.env 도 함께 보존)
지우는 것staging 예
PM2openmake-llm-staging openmake-next-staging openmake-litellm-staging openmake-bench-staging …
dockeropenmake-staging-postgres openmake-staging-redis openmake-staging-searxng + 볼륨
프록시~/.openmake/caddy/caddy.d/staging.caddy
디렉터리~/.openmake/staging

남기는 것: 런타임 이미지(--purge-images 로 지운다), DB 백업, 호스트 공용인 기본 모델 서버와 프록시.

DB 백업

omk env backup <env>                 # 지금 한 번 → ~/.openmake/backups/<env>/
omk env backup <env> --list
omk env backup <env> --schedule      # 매일 03:30
omk env backup <env> --off

# 복원 — 그 환경 디렉터리에서
cd ~/.openmake/<env>/llm && ./openmake_llm.sh db-restore <파일>

백업은 환경 디렉터리 밖에 쌓인다 — reset 으로 환경을 지워도 남는다.

11 · 자동 검사

무엇이 자동으로 막아 주는가

개발 인원이 늘어도 흐름이 지켜지려면, 사람이 기억하는 규칙이 아니라 저장소가 막아야 한다. 아래는 어디에서 무엇이 검사되는지다.

어디서 무엇을 검사하나

단계검사보는 것누가
① 로컬 개발로컬 테스트테스트 · lint개발자
② feature/* → devCI Gate계약 · 의존성 감사 · 테스트 · 빌드 · 크기 · lint자동
③ 환경 dev설치 확인설치해서 도는가, 기능사람
④ dev → mainCI Gate② 와 같음자동
⑤⑥ 환경 stagingupdate 확인 · verify마이그레이션, 합쳐진 기능사람
⑧ 환경 online릴리스 게이트 · 스모크⑥ 의 기록이 있는 릴리스인가자동 + 사람

CI 는 한 번에 40분쯤 걸린다. 그래서 ① 에서 로컬 테스트를 먼저 돌린다.

maindev
PR 로만 합친다예예
CI Gate 통과 필수예예
force push · 삭제금지금지
리뷰 승인 필수아니오아니오 — 인원이 늘면 켠다
이 표는 목표 상태다

브랜치 보호는 저장소 파일이 아니라 GitHub 설정이다. dev 의 보호는 워크플로 수정이 dev 에 들어가 CI 가 한 번 통과한 뒤에 건다 — 먼저 걸면 아무도 머지할 수 없다. 지금 상태는 아래 명령으로 본다.

gh api repos/openmake/openmake_llm/branches/dev/protection

의존성 감사에 걸렸을 때

CI 의 Gate 0.7 은 운영 의존성에 high 이상 보안 권고가 새로 생기면 실패한다. 내 변경과 무관하게 어느 날 갑자기 실패할 수 있다.

npm run audit:gate                                   # 무엇이 걸렸는지
npm ls <패키지> --omit=dev                          # 누가 끌어오는지
npm update <패키지> --package-lock-only             # 고친 버전이 있으면 lockfile 만 올린다
npm run audit:gate

당장 올릴 수 없으면 사유와 만료일을 적어 .audit-allowlist.json 에 넣는다. 만료가 지나면 다시 실패한다.
