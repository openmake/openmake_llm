개발에서 운영까지 · 8단계

local MacBook에서 개발하고 GitHub가 dev/main 검사를 처리합니다. tom은 main을 설치·검증하고, 사람의 실사용 OK 후 검증된 릴리스만 ome-on으로 이어집니다.

합의 흐름 원본 · 현황 보드 · 실행 명령과 활성화 조건

local 개발·테스트·PR → PR CI·dev 자동 병합
 → 병합 dev CI·기본/변경 기능 검사 → main 자동 승격
 → tom 설치·검증·SHA 고정 → 사람 실사용 OK·verify
 → 검증 릴리스 자동 발행 → ome-on 고정 태그 설치·스모크
bean ── 주기적 외부 실사용 검사 ──▶ tom / ome-on
단계담당하는 일진입점

역할과 판정

별도 배포 dev 서버는 필수 구성에서 폐지됐습니다. dev는 Git 브랜치이며 local은 개발 호스트입니다. 사람의 판단은 1번과 6번에 있습니다. bean은 검증·배포 담당을 대신하지 않습니다.

문서·소스 구현, 로컬 검사, 원격 활성화, 실제 단계 완료를 구분합니다. 보드의 기록 미연결을 성공이나 실패로 단정하지 않습니다.

단계별 실행과 다음 조건

1
local · 사람+에이전트

개발·관련 테스트·PR

origin/dev에서 작업 브랜치를 만들고, 변경 기능 회귀 테스트·lint·필요 빌드 후 dev PR을 올립니다.

omk dev up
2
GitHub · 자동

작업 PR → dev

최신 PR 변경의 CI와 결정적 구조 검사를 충족하면 일반 병합합니다. 사람 PR 승인 단계는 없습니다.

auto-merge workflow
3
GitHub runner · 자동

병합 dev 소스·기능 검사

실제로 병합된 SHA의 소스/DB/빌드/린트와 임시 앱 기본 스모크+신규·수정 기능/관련 소스를 검사합니다. 전체 E2E를 무조건 돌리지 않습니다.

npm run test:dev -- FULL_SHA
4
GitHub · 자동

dev → main 승격

현재 dev push CI 통과와 최신 main 조합의 PR CI가 모두 필요합니다. 폐지된 별도 dev 서버나 omk/env-dev 표지는 요구하지 않습니다.

promote workflow
5
tom · 자동

설치·스모크·필수 검증

main 설치 후 기본 스모크와 구성된 필수 고강도 검증을 수행합니다. 성공한 설치 SHA를 사람 확인을 위해 고정합니다.

omk env pipeline staging
6
사람 + tom 명령

실사용 OK → verify

사람이 고정된 tom을 직접 써보고 OK하면 동일 SHA를 명령으로 기록합니다. 실행/디스크 빌드·고정 SHA·검증 근거를 다시 대조합니다.

omk env approve staging --sha FULL_SHA --yes
7
GitHub · 자동

검증 릴리스 발행

verified ref와 각 커밋의 metadata-only 계보 및 릴리스 PR CI를 확인하고 release-please PR을 자동 병합합니다. 추가 사람 승인은 없습니다.

release-verified / release-please
8
ome-on · 자동

고정 태그 설치·운영 스모크

한 번 선택한 태그 SHA를 검증하고 백업 후 관리형 갱신합니다. 설치/실행 SHA 일치와 스모크 통과가 완료 조건입니다.

omk env pipeline online
03 · 로컬 개발

로컬 개발 — 고치면서 바로 본다

로컬 장비의 작업 클론 안에서 쓴다. 환경이 아니다 — ~/.openmake 아래에 두지 않고, 인스턴스 이름 local 로 앱이 PM2 없이 포그라운드에서 돈다.

명령

scripts/env/omk.sh dev setup          # 최초 1회 — 툴체인·.env·의존성·DB·마이그레이션·검색·런타임 이미지·게이트웨이·기본 모델
scripts/env/omk.sh dev up             # DB/Redis/SearXNG/게이트웨이 + api + web (+ bench) — Ctrl+C 로 종료
scripts/env/omk.sh dev up api         # 개별: deps | api | web | bench
scripts/env/omk.sh dev up --tailscale # 다른 기기에서 보기 (또는 --host <이름|IP>)
scripts/env/omk.sh dev status
scripts/env/omk.sh dev down           # DB/Redis/SearXNG/게이트웨이 정지 (데이터 유지)
scripts/env/omk.sh dev reset          # 컨테이너·볼륨 삭제 (소스·.env 유지). --keep-data 면 볼륨은 남긴다

openmake_bench 가 옆 디렉터리(../openmake_bench)에 있으면 같이 띄운다.

setup 옵션

환경 설치(omk env install)와 이름도 뜻도 같다.

옵션하는 일
--no-runtime-images런타임 이미지(약 7GB) 빌드를 뺀다. 에이전트 작업·아티팩트 내보내기는 동작하지 않는다
--no-searxng웹 검색 컨테이너를 뺀다
--no-litellm게이트웨이를 뺀다 — .env 의 LLM 주소를 직접 채워야 한다
--no-default-model기본 모델(1.7B)을 띄우지 않는다
--llm-base-url U --llm-model M게이트웨이 뒤에 둘 업스트림. 이미 있는 Ollama 등 (--llm-api-key K 는 선택)
 
# 예 — 이미 있는 Ollama 를 쓰고, 이미지 빌드는 뺀다
scripts/env/omk.sh dev setup --no-runtime-images \
  --llm-base-url http://localhost:11434/v1 --llm-model <모델 이름>

고친 뒤 할 일

코드만 고쳤으면 dev up 재시작, 설치되는 것이 바뀌었으면 dev setup.

고친 것할 일
웹 화면 apps/web없음 — 저장하면 바로 반영
API apps/apidev up 을 끄고 다시 띄운다 — API 는 감시 재시작이 없다
공용 패키지 packages/*npm run build:packages → dev up 재시작
의존성 package.jsondev setup
DB 마이그레이션dev setup
런타임 이미지 Dockerfiledev setup
omk.sh · 설치 스크립트dev setup
setup 을 다시 돌릴 때

dev up 을 먼저 끈다 — .env 가 바뀌면 API 를 어차피 다시 띄워야 한다. dev setup 은 지우지 않는다: DB 볼륨과 .env 의 기존 값(비밀번호·암호화 키)은 그대로 두고 없는 것만 채운다. 지우는 것은 dev reset 이다.

환경과 같은 것, 다른 것

검색·런타임 이미지·게이트웨이·기본 모델은 환경 설치와 같은 함수(stack_ensure)로 준비한다. 그래서 설치 직후 바로 채팅이 된다. 다른 것은 셋뿐이다.

  • 앱을 빌드하지 않는다 — ts-node · next dev 로 돈다
  • 앱을 PM2 에 올리지 않는다 — concurrently 아래 포그라운드
  • .env 의 NODE_ENV 가 development 다

호스트의 환경들과 같이 쓰는 것, 따로 두는 것

같이 쓰는 것 (호스트에 하나)따로 두는 것 (local)
Docker 엔진 — macOS 는 Colima VM openmakePostgreSQL · Redis (openmake-local-*) — 브랜치의 마이그레이션이 환경의 DB 를 바꾸지 않게
기본 모델 서버 — PM2 omk-llamacpp. 모델 1.8GB 는 한 번만 받는다게이트웨이 — PM2 openmake-litellm-local. 환경이 없어도 채팅이 된다
런타임 이미지의 레이어 (캐시 재사용)런타임 이미지의 태그 :local · SearXNG · 작업 공간
  • .env 의 LLM_BASE_URL 을 직접 넣어 둔 작업 클론은 건드리지 않는다. omk 가 바꾸는 것은 비어 있거나, 자리표시자(http://localhost:4000 인데 그 포트에 아무것도 없음)이거나, omk 가 넣은 게이트웨이 주소일 때뿐이다.
  • 게이트웨이와 기본 모델 서버는 dev up 의 Ctrl+C 뒤에도 남는다. 재부팅 등으로 내려가 있으면 dev up 이 다시 띄운다.
  • 작업 클론이 여럿이면 게이트웨이 하나(local)를 같이 쓴다.

병합 dev 검사 · GitHub runner

전용 개발 서버 설치를 main 승격의 전제로 두지 않습니다. GitHub에서 실제 병합 dev SHA의 CI를 수행합니다.

소스와 실행 기능

  • 기존 단위/DB 통합 테스트·빌드·lint·Base/Add-on 경계 검사를 유지합니다.
  • 격리된 임시 앱/DB/model fixture로 앱 기동·DB·로그인·기본 채팅·웹 응답을 확인합니다.
  • 변경 기능/관련 소스 테스트를 선택합니다. 전체 브라우저 테스트를 일괄 실행하지 않습니다.
  • 선택할 검사가 없거나 미실행이면 통과로 숨기지 않습니다. 실패 시 local에서 수정합니다.

fixture 검사는 실제 모델 품질 검증이 아닙니다. 통과한 dev SHA만 승격하고, main 조합이 바뀌면 PR 검사도 다시 필요합니다.

tom · main 설치와 사람 확인

main 설치 → 스모크 → 필수 검증 → 설치 SHA 고정까지 자동화합니다. 빈 검증 설정은 차단합니다.

omk env pipeline staging
omk env pipeline staging --schedule '*/10 * * * *'
# 사람이 실제로 사용한 뒤 OK한 동일 SHA
omk env approve staging --sha FULL_SHA --yes

검증 중 hold로 자동 갱신을 막고 실행/디스크 빌드와 검증 결과를 대조합니다. 취소 후 새 설치본을 확인하려면 omk env hold staging --release로 해제합니다.

6번 버튼 연동은 모니터 계약을 따릅니다. 웹 인증·권한·CSRF를 확인하고 고정 argv만 실행해야 합니다. 중앙 모니터 소스가 없으므로 버튼이 이미 연결됐다고 표시하지 않습니다.

ome-on · 검증된 태그만 설치

omk env pipeline online
omk env pipeline online --schedule '*/10 * * * *'
omk env pipeline online --off

captured 태그 SHA의 검증 계보를 확인하고 기존 백업·관리형 배포를 사용합니다. 배포 중 latest를 다시 선택하지 않습니다. 설치/실행 SHA가 고정 태그 SHA와 같고 스모크가 통과해야 완료입니다.

운영 업데이트 스모크와 bean의 주기적 외부 검사는 별개입니다. OS 자동기동 권한과 재부팅 복원은 호스트별로 검증합니다.

verify → 릴리스의 코드 계보

refs/omk/verified/FULL_SHA가 사람 확인 뒤의 검증 기록입니다. verify는 단순 health 확인을 넘어 고정 SHA·필수 검증·실행 빌드 일치를 요구합니다.

릴리스 PR과 태그는 verify의 자손이며 모든 중간 커밋이 허용된 버전/변경 로그 메타데이터여야 합니다. JSON 버전 외 의존성 변경이나 기능 변경은 되돌려도 차단합니다. 허용 경로는 검증된 설정에서 읽습니다.

릴리스 PR 최신 CI와 계보를 검사한 뒤 자동 병합하고 release-please가 태그·릴리스·SBOM/증명을 생성합니다. 코드 포함과 검증 완료는 별도 사실입니다.

08 · 설치

아무것도 없는 호스트에서 한 줄

옵션 없이 설치하면 게이트웨이와 기본 모델까지 채워져, 채울 것 없이 채팅이 된다.

# macOS / Linux / WSL2
curl -fsSL https://raw.githubusercontent.com/openmake/openmake_llm/main/scripts/env/omk.sh \
  | bash -s -- env install staging --tailscale

curl -fsSL https://raw.githubusercontent.com/openmake/openmake_llm/main/scripts/env/omk.sh \
  | bash -s -- env install online  --public-url https://chat.example.com

Windows 네이티브는 지원하지 않는다 — WSL2(Ubuntu) 안에서 같은 스크립트를 쓴다(omk.ps1).

한 번에 되는 일

  1. git 확인 → openmake_llm 클론
  2. install.sh --minimal — Node 24 · Docker · PM2, .env 시크릿, PostgreSQL · Redis, 마이그레이션, 빌드, PM2 기동, health
  3. 웹 검색(SearXNG) → 런타임 이미지 → LiteLLM 게이트웨이 (업스트림을 주지 않았으면 기본 모델까지)
  4. --bench 를 줬을 때만: openmake_bench
  5. Caddy 프록시 → --tailscale / --host 를 줬으면 그 주소 허용
  6. ~/.openmake/bin/omk 래퍼

2 가 실패하면 설치가 멈춘다. 3 의 실패는 경고만 남기고 계속한다. 4 는 실패하면 멈춘다.

설치 후 사람이 채울 것

해당할 때만 요약 끝에 [할 일] 로 나온다.

나오는 경우할 일

macOS — 전용 Colima

macOS 의 OpenMake 는 전용 Colima VM(프로필 openmake)에서 컨테이너를 돌린다. Docker Desktop 설치는 선택 사항이며, 기존 OpenMake 데이터 이전과 확인을 마치면 제거해도 된다. OpenMake 명령은 기본 Docker 컨텍스트와 무관하게 Colima 를 선택한다.

docker --context colima-openmake ps      # openmake 의 컨테이너 보기
colima status --profile openmake
09 · 복구

꼬였을 때 — 지우고 다시

reset 은 환경 이름만으로 지울 대상을 계산한다. .env 가 깨졌어도 동작한다.

online 에는 쓰지 않는다

omk env reset online 은 DB 볼륨까지 지운다. 옮길 때는 db-dump → db-restore.

omk env reset staging --reinstall            # 전부 지우고 같은 브랜치로 재설치
omk env reset staging --keep-env --reinstall # .env(LLM 키·API 키)는 백업했다가 복원
omk env reset staging --keep-data            # DB 볼륨은 남김 (.env 도 함께 보존)
지우는 것staging 예
PM2openmake-llm-staging openmake-next-staging openmake-litellm-staging openmake-bench-staging …
dockeropenmake-staging-postgres openmake-staging-redis openmake-staging-searxng + 볼륨
프록시~/.openmake/caddy/caddy.d/staging.caddy
디렉터리~/.openmake/staging

남기는 것: 런타임 이미지(--purge-images 로 지운다), DB 백업, 호스트 공용인 기본 모델 서버와 프록시.

DB 백업

omk env backup <env>                 # 지금 한 번 → ~/.openmake/backups/<env>/
omk env backup <env> --list
omk env backup <env> --schedule      # 매일 03:30
omk env backup <env> --off

# 복원 — 그 환경 디렉터리에서
cd ~/.openmake/<env>/llm && ./openmake_llm.sh db-restore <파일>

백업은 환경 디렉터리 밖에 쌓인다 — reset 으로 환경을 지워도 남는다.

알아 둘 것

  • staging / online 외의 이름도 된다 (omk env install qa --ref feature/x). local 은 로컬 개발이 쓰는 이름이라 환경 이름으로 쓸 수 없다.
  • 환경 이름을 생략한 omk env … 는 오류다.
  • bench 는 기본으로 설치하지 않는다 — --bench 를 줄 때만 붙는다.

자동 검사 · 활성화와 남는 경계

도입 조건

  • 자동화 workflow와 신뢰된 스크립트가 기본 브랜치에 존재해야 합니다.
  • dev/main의 필수 CI와 strict 최신 기준, 저장소 auto-merge가 필요합니다.
  • OMK_AUTOMATION_TOKEN과 tom/ome-on 실제 스케줄·QA 계정·필수 검증 시나리오를 준비해야 합니다.
  • credential이 없거나 검사가 실패하면 오류/대기로 기록하며 성공 skip으로 숨기지 않습니다.

bean과 모니터

bean은 대상별 시나리오·주기·관측 SHA/버전·근거를 기록합니다. 주기를 임의 활성화하지 않으며 사람 OK·verify를 대신하지 않습니다.

중앙 보드 소스가 로컬에 없어 기존 7단계 API를 변경·배포하지 않았습니다. 새 8단계 증거 연결과 6번 버튼의 실제 서버 구현은 연동 계약을 기준으로 합니다.
